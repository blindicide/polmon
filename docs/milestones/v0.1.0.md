# Milestone v0.1.0 — Phase I MVP

VERSION: v0.1.0
STATUS: PASS

IMPLEMENTED: The Phase I MVP and its target demonstration. `polmon-demo` drives the documented HTTP
API (same `ApiClient` as the Windows GUI) through health → topology validate/load → admitted
deployment → controlled experiment → telemetry/capture → report → reset → independent kernel-level
cleanup check, exiting non-zero on any unmet step. Demonstration inputs:
`examples/topologies/mvp-demo.yml` (50 L0 sensors, 2 L1 servers with the built-in HTTP service,
one isolated 10.70.0.0/24 network) and `examples/scenarios/mvp-recon.yml` (controlled
reconnaissance of declared lab nodes only). Defects found by reading the demonstration's own report
and fixed: telemetry resource samples recorded 0 active endpoints/namespaces during experiments
(now live counts plus topology deployment time), and a failure condition that correctly did not
fire was rendered as `MISMATCH` (now role + outcome: met/not met, triggered/not triggered).
MVP REQUIREMENTS → EVIDENCE:
- Linux backend: FastAPI `polmon-backend`; API contracts in docs/API.md; used by the demo over HTTP.
- Standalone Windows client: `polmon-0.1.0-windows-x64.exe` built, tested, and smoke-tested
  (`--version`, `--self-test`) on GitHub-hosted Windows; remote control of real L1 since v0.0.11.
- Declarative topologies: YAML with schema validation, lab address ranges, resource estimation.
- Functional L0 endpoints: 50 in the demo; benchmarks 10–250 with 0% loss.
- Functional L1 endpoints: 2 namespaces with reachable HTTP services in the demo.
- Hybrid L0/L1 communication: L0→L1 ICMP across one shared TAP in the demo (2/2 reachable).
- Basic scenario engine: closed actions, deterministic sequence, conditions, cleanup policy.
- Telemetry and reporting: 11 structured events, 15 PCAP frames, JSON + Markdown report.
- Resource admission control: 429 on excess (v0.0.15 evidence); limits in every benchmark.
- Automated environment cleanup: reset, SIGINT/SIGTERM shutdown cleanup, `lab-cleanup.sh`.
- Reproducible benchmark results: three recorded runs retained with raw JSON/CSV and summaries.
- Documented build and release procedures: BUILD-WINDOWS, CI, RELEASE (incl. tag repair), scripts.

CPUs visible, 7.8 GiB RAM, shared with other services; `benchmarks/results/SUMMARY-v0.1.0.md`):

The engineering target (50 L0 + 2 L1 within ≈1 GB incremental memory) is met on this host by a wide
margin on both measures. In the live demo the backend process grew 68 KiB on deployment.
KNOWN LIMITATIONS: Measurements come from one shared host; the 2-core/2-GB budget is enforced by
admission and default limits, not by running on such a machine. L1 kernel memory is only
approximated by the noisy host MemAvailable delta. Hybrid L1→L0 traffic and any L0 TCP are
unsupported and reported as such. L2 is not implemented. A backend killed with SIGKILL cannot
clean up; `scripts/lab-cleanup.sh` recovers. Tags v0.0.2 and v0.0.2+windows.1 have no Release of
their own; the v0.0.2 Windows pipeline was released as v0.0.2+windows.2 (see v0.0.2 report).
